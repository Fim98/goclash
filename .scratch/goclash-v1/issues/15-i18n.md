# 15: 界面多语言（简体中文 / English）

**What to build:** 设置页一直躺着一个不生效的 `language` 字段。这张票把它接上：全站文案可切换，选择持久化，托盘浮窗（独立 webview）跟随同一个设置，出口地区名跟着界面语言走。

**Blocked by:** 13 (深色主题，路径上最后一张 UI 票)

**Status:** done

- [x] `lib/i18n.tsx`：零依赖的翻译层。**中文原文即键**——`t("已连接")` 在 zh-CN 下原样返回，en-US 查表；`MessageKey = keyof typeof EN` 让漏翻的字符串变成编译错误而不是空白标签，复制文案的 diff 也只有一行
- [x] 占位符 `{name}`，值缺失时保持 `{name}` 可见（拼错参数名应该看起来不对，而不是让句子静默丢数字）
- [x] `LocaleProvider` + `useT()`：App 持有状态，设置页通过 context 即时切换；`localStorage` 缓存让首帧就是正确语言，随后与 settings.json 对账
- [x] 全部 7 个页面、外壳、托盘浮窗、状态面板约 250 条文案全部走 `t()`；策略组/节点名、日志内容是订阅与内核的数据，**有意不翻**
- [x] 设置页「界面语言」从只读文本变成 分段选择（简体中文 / English，各自以母语显示）；选择写回 `updateSettings({ language })`
- [x] 托盘浮窗自己读 settings 并包一层 Provider——它是独立 webview，不继承主窗口的 React 树
- [x] 出口地区：网关在 `exitRegion` 之外新增 `exitRegionCode`（ISO 码），前端 `lib/regions.ts` 按界面语言重新命名，未知代码回退到网关给的原始值。英文窗口不再出现「中国香港」
- [x] Go：`Settings.Language` 默认 `zh-CN`；加载时把旧值（"简体中文"/"English"/任意垃圾）归一化成代码，前端只见两种合法值
- [x] 筛选标签（全部/代理/直连/拦截）与日志等级、规则类型（DOMAIN、IP-CIDR…）都进了同一张键表——后者是两种语言下写法相同的协议 token，声明成恒等条目以保持「每个渲染字符串都是被检查的键」这条不变量
- [x] 测试：i18n 单测 5 条（zh 原样、en 查表、占位符缺失可见、旧值归一化、locale 枚举）+ 设置页 2 条（切英文后整窗重绘并写回网关、按 settings.json 里的语言启动）+ 既有 73 条全部保持中文断言通过（重构没有碰坏任何原文）

## Comments

- **为什么不用 i18next**：那套框架解决的是「几百个 key 的命名与命名空间」问题，而这里用中文原文当键，键表本身就是文案清单。真正的收益在类型检查：`t("已连搂")` 编译不过。代价是中文文案改动必须同步改英文表——这本来就是要做的事，只是从「忘了」变成「编译不过」。
- **为什么数据不翻**：节点名「香港 · IPLC 02」来自机场订阅，日志来自内核输出。翻译它们等于伪造用户数据。出口地区是唯一例外——它由我们自己在网关里从 ISO 码映射而来，属于「我们生成的文案」，所以挪到前端按语言渲染。
- **托盘为什么单独接**：420×620 浮窗是独立 webview，加载 `/?window=tray`。它读同一个 settings.json，两边语言永远一致；localStorage 缓存同样生效，浮窗首帧不闪中文。
- **lint 取舍**：`react-refresh/only-export-components` 要求一个文件只导出组件，而 i18n 模块天然导出 provider + hooks + 纯函数。仓库对 shadcn 的 `components/ui/**` 已有同样的豁免先例，这里照做并在注释里写明理由——为热重载规则拆散文件，会牺牲「键被类型检查」这条真实不变量。
- **验证**：英文界面在 1440×900（首页/设置）与 420 浮窗逐屏截图核对过，长文案没有撑破任何卡片；中文界面由既有 73 条断言原文的测试守住。
